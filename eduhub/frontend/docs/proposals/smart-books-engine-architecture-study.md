# EduHub Smart Books Engine — Architecture Study

**Status:** Research/architecture document. No implementation has started. Every claim below is grounded in a specific file and line from the current codebase (backend: `eduhub-backend`, frontend: `eduhub-studio-test`) — where something was searched for and not found, that is stated explicitly rather than inferred.

**Approved as the architectural foundation for Smart Books**, with the synchronization-specific findings in §6/§7/§9/§11 generalized into a platform capability — see the companion document, [`universal-synchronization-engine-technical-spec.md`](universal-synchronization-engine-technical-spec.md), which is the agreed target-state design. The phased roadmap in §10 reflects that agreement.

---

## 1. Current Architecture Overview

EduHub is a dual-backend system (per `CLAUDE.md`): a Google Apps Script legacy plane for points/wallet/config, and a Render-hosted FastAPI backend (`eduhub-backend/server.py`, ~7,800 lines, plus ~40 `register_*_routes(api, db, ...)` sibling modules using explicit dependency injection — a deliberate post-refactor convention replacing an older `exec()`-into-namespace pattern). The frontend is a single CRA/CRACO React 19 PWA (`eduhub-studio-test`).

Three student/teacher-facing surfaces matter for this study:
- **Authors Studio** (`/studio`, `src/studio/`) — a teacher/admin CMS, Google-OAuth-gated (`StudioAuth.jsx`) against an admin allowlist. Composed of ~34 independent tab panels (`*Studio.jsx`), each backed by its own `register_*_routes` module.
- **Books Library** (frontend `src/eduhub/pages/library/`) — the student-facing catalog and reading surface.
- **Reader Engine** (`src/eduhub/pages/library/reader/`) — the distraction-free book-reading UI, mounted outside the main app shell.

**Books Engine** is not one module — it is the composite of:
- `server.py`'s direct book CRUD (`list_books`, `get_book`, `studio_save_book`, `studio_upload`, `studio_parse` — manual authoring path)
- **Book Factory** (`book_factory_*.py`, 9 files) — an AI-assisted *draft generation* pipeline, entirely separate from the manual path, that never writes to `db.books` itself; it produces a draft the author explicitly reviews and hands off to the manual save path.

## 2. Existing Media Flow

**Book text/blocks:** authored directly as JSON on the book document (no file storage) — either typed in `StudioEditor.jsx`, parsed from an uploaded `.docx`/`.txt`/`.md` via `POST /api/studio/upload` (`server.py:1319-1340`, using `content_parser.py`), or generated by Book Factory.

**Generated audio/images** (the *only* binary media in the system) flow through two storage backends, chosen automatically per call site:

| Content | Generator | Storage | Fallback |
|---|---|---|---|
| Chapter narration audio | ElevenLabs TTS (`server.py:_elevenlabs_generate`) | Cloudflare R2 (`_upload_audio_to_r2`) | GridFS bucket `studio_audio` |
| Multi-speaker conversation audio | ElevenLabs TTS per line (`server.py:_elevenlabs_generate_line`) | R2 (`book_factory_conversation.py`, key `conversation-lines/{jobId}/{chapterId}/{lineId}/{attemptId}.mp3`) | none found |
| Book Factory cover images | Gemini image model (`book_factory_image.py`) | R2 (`book-covers/{jobId}/{attemptId}.{ext}`) | none — export falls back to author's manual `coverImage` string |
| Hero compositing artwork (Welcome Experience) | admin upload | R2 (`hero-artwork/{assetId}.{ext}`) | **none** — `HTTPException(503)` if R2 env vars absent |
| Voice Treasure mission images | Gemini image model | GridFS (primary) | R2 mirror (best-effort, optional) |
| Student avatar / AI Assistant voice recordings / EduTalk audio cache | upload / TTS | R2 | none in the modules checked |

**Book covers specifically**: `coverImage` is a plain string field on the book document (`server.py:422`), populated either by an admin pasting *any* URL into a free-text input (`StudioEditor.jsx:753`) or by Book Factory's Gemini-generated R2 URL. There is no dedicated cover-asset table or validation that a pasted URL is even reachable.

**Serving:** R2 URLs are served directly (plain public `https://pub-<hash>.r2.dev/...` or custom domain, no signing, no CDN-proxy route). GridFS audio is streamed via `GET /api/studio/audio/{filename}` with real HTTP Range support (added specifically to fix iOS Safari scrubbing). The frontend's `media-urls.js` has an explicit `isR2PublicHost()` predicate and passes R2 URLs through unchanged.

**Upload pipeline** (`StudioUpload.jsx` → `POST /api/studio/upload`): accepts `.docx/.txt/.md` only, for *text extraction into chapter blocks*. **The uploaded file itself is never persisted** — only the parsed JSON is returned to the browser. There is no audio/video upload pipeline anywhere in Author Studio today; every audio/image asset in the system is either AI-generated or a manually-pasted external URL.

## 3. Existing AI Flow

**Gemini** is the only image/text generation provider, called via raw `httpx` REST to `generativelanguage.googleapis.com` (no Google SDK dependency exists in `requirements.txt`). It is integrated **independently in at least 8 separate modules**, each with its own prompt-building, retry logic, and error taxonomy:

| Module | Purpose | Model (default) |
|---|---|---|
| `book_factory_gemini.py` | Book Factory blueprint + chapter text | `gemini-2.5-flash` |
| `book_factory_image.py` | Book Factory cover images | `gemini-3.1-flash-image` |
| `gemini_engine.py` | Author Studio "AI Scene Builder" | `gemini-2.5-flash` |
| `voice_treasure_gemini.py` | Mission images + multimodal speech evaluation | separate image/eval models |
| `ai_assistant_tools.py` | Student AI Assistant chat | `gemini-2.5-flash` |
| `ai_assistant_voice_tools.py` | Text feedback on voice-mission transcripts | `gemini-2.5-flash` |
| `premium_ai_tools.py` | Khmer Decoder / Executive Tone Upgrade (exposes shared `_post_gemini` reused by `edutalk_tools.py`, `edutalk_live_tools.py`) | `gemini-2.5-flash` |
| `edutalk_live_tools.py` | **Real-time Gemini Live** voice-to-voice coaching + post-session text report | `gemini-3.1-flash-live-preview` |

Only `book_factory_gemini.py` and `book_factory_image.py` share a genuine common taxonomy (`BFRetryableError`/`BFUnknownOutcomeError`/`BFTerminalError`, imported by the image module from the text module). `premium_ai_tools._post_gemini` is the closest thing to a second shared primitive. Otherwise, **there are effectively 6+ independently-written Gemini HTTP clients** doing the same fundamental thing (build prompt → POST → parse JSON) — a real duplication risk called out in §7.

**ElevenLabs** is text-to-speech only (never speech-to-text), called from exactly two functions in `server.py` (`_elevenlabs_generate`, `_elevenlabs_generate_line`) and reused by every other module that needs narration/dialogue audio — this one *is* correctly centralized, unlike Gemini.

**Claude/Anthropic: not found.** Grepped both repositories (case-insensitive) for `anthropic`, `claude-`, `ANTHROPIC_API_KEY`, `claude_api` — zero matches anywhere, including `requirements.txt` and `package.json`. There is no Claude integration, no SDK dependency, no key variable, no call site. Any future integration would be entirely new.

**Speech recognition**: the only STT in the system is the **browser's native Web Speech API** (`ai_assistant_voice_tools.py:126`), client-side, for voice-mission transcripts — not a backend AI call. EduTalk Live Coach uses Gemini Live's bidirectional audio (student mic → EduHub backend WebSocket → Gemini Live → back), which is real-time understanding+response, not a transcription-and-store pipeline. **No backend ASR/forced-alignment service exists for arbitrary uploaded audio or video.**

## 4. Existing Rendering Flow

Lifecycle of a manually-authored book:
```
Author writes/imports text in StudioEditor.jsx
        ↓
POST /api/studio/books  →  db.books (append-only revisions, sorted by `revision`)
        ↓
GET /api/books/{slug}  →  latest revision, guest-content-boundary applied
        ↓
Library frontend renders catalog card
        ↓
Reader Engine (src/eduhub/pages/library/reader/) mounted outside AppShell
        ↓
ChapterBlocks.jsx renders each block by type (paragraph/transcript/dialog/mcq/image/audio/...)
```

Lifecycle of a Book-Factory-generated book:
```
Admin starts a job (BookFactoryStudio.jsx)
        ↓
book_factory_jobs.py: atomic per-stage claim → book_factory_gemini.py (blueprint, then each chapter)
        ↓
Optional stages: book_factory_image.py (cover), book_factory_narration.py (paragraph→transcript
  block conversion), book_factory_conversation.py (per-line dialogue audio via ElevenLabs)
        ↓
book_factory_composer.py assembles canonical book JSON; book_factory_validator.py checks it
        ↓
Author reviews/edits the draft in StudioEditor (handoff via editorSeed, NOT auto-published)
        ↓
Same manual save path as above (POST /api/studio/books)
```

Books never auto-publish from Book Factory — a human always reviews before the content reaches `db.books`.

`db.books` document shape (from `CANONICAL_BOOK_FIELDS`, `server.py:3407-3413`): `slug, title, subtitle, author, section, coverEmoji, coverImage, coverGradient, accent, badge, level, readingMinutes, price, tier, published, newUntil, contentType, format, chapters, content, revision, _authoredAt, _authoredBy, ai_voice`. `tier` is decorative only (reading-mode visual treatment) and is explicitly decoupled from pricing — `price` is the real monetization field (confirmed during this session's guest-content-boundary work).

## 5. Existing Storage Strategy

| Layer | Technology | Owner(s) |
|---|---|---|
| Book/job/config documents | MongoDB (append-only revisions for books) | `server.py` (books), `book_factory_jobs.py` (jobs, never touches `db.books`) |
| Generated media (audio/images) | Cloudflare R2 (`boto3` S3-compatible client), real and working — `endpoint_url=https://{ACCOUNT_ID}.r2.cloudflarestorage.com`, 5 env vars (`R2_ACCOUNT_ID/ACCESS_KEY_ID/SECRET_ACCESS_KEY/BUCKET_NAME/PUBLIC_URL`) | 8 modules, one shared bucket, distinguished by key prefix |
| Media fallback | GridFS — 3 buckets found total: `studio_audio` (ElevenLabs narration fallback), `tuition_receipt_files` (unrelated to books), `voice_treasure_media` (R2-mirror pattern) | `server.py`, `tuition_receipt_files.py`, `voice_treasure_media.py` |
| Session/auth | Two separate Mongo-backed cookie sessions: `user_sessions` (admin/teacher, Google OAuth) and `student_sessions` (student login, Bearer-token fallback for iOS Safari ITP) | `server.py` |

All R2 code paths degrade gracefully **except** Hero Artwork, which is R2-or-nothing (`HTTPException(503)` if env vars absent) — every other media path falls back to GridFS or a bundled default.

## 6. Existing Synchronization Capabilities

This is the most important finding for the Smart Books proposal: **a real, working, word-level synchronization system already exists** — not called "teleprompter," but functionally equivalent, built for narration and conversation audio.

**Backend:** `_elevenlabs_generate`/`_elevenlabs_generate_line` convert ElevenLabs' character-level alignment into word-level `{word, start, end}` timestamps. For chapter narration, these are distributed across `transcript`-type blocks *proportionally by character count* (`server.py:1215-1238`) — **this is an approximation, not a true per-word mapping across block boundaries** (see gap in §7). For conversation/dialogue, each line gets its own exact word timestamps (no cross-block slicing needed, since each line is one ElevenLabs call).

**Frontend:**
- `ChapterBlocks.jsx`'s `TranscriptParagraph`/`computeTimestampActiveWord` — binary-search word-highlighting during playback, with a documented **two-mode fallback**: exact-timestamp mode when `wordTimestamps` exist, "weighted-estimation" mode (proportional, no real data) for blocks with only approximate `start`/`end` (e.g., manually-uploaded MP3s with no per-word data at all).
- `DialogTurn.jsx`'s `WordSync`/`computeWordSyncActiveWord` — the same word-highlight mechanism, plus **per-speaker color assignment**, speaker labels, and an `emotion` field. This already covers "speaker highlighting" and "conversation mode" from the requested feature list.

**What does NOT exist:** sentence-level highlighting, paragraph-level highlighting, karaoke mode, shadowing mode, storytelling mode, auto-scroll tied to playback, adjustable playback speed, sentence/paragraph replay, or any admin toggle for these features. All synchronization today is word-level only, always-on (no per-book configuration), and only available for AI-generated (ElevenLabs) audio — **there is no speech recognition or forced-alignment pipeline for uploaded/pre-recorded audio or video**, so a teacher's own MP3 upload gets only the coarse "weighted-estimation" fallback, never real timestamps.

**Existing interaction-runtime (highly relevant prior art):** `book_factory_interaction_planner.py` — internally named **"Signature Smart Interactive Book"** — already implements a tier-gated, deterministic, density-budgeted system choosing which of 8 interaction types (`reveal, mission, pronunciation, matchpairs, responsechoice, sentencebuilder, checkpoint, branchdialog`) a chapter may use, plus a `vocabgrid` baseline type. This is a working precedent for exactly the "admin configures features per book, reader adapts without separate formats" principle the Smart Books vision calls for — it should be studied closely (not rebuilt) when designing per-book feature configuration.

## 7. Architectural Gaps

1. **No ASR/forced-alignment for uploaded media.** Every synchronization primitive that exists is a byproduct of *generating* audio via ElevenLabs, which returns alignment for free. There is no pipeline to take an uploaded human-recorded audio/video file and produce word timestamps — this is the single largest gap standing between the current system and the "Intelligent Media Processing" pipeline requested (Upload → Storage → Audio Extraction → Speech Recognition → Speaker Detection → Word/Sentence/Paragraph Timestamps → Confidence → Sync Model). None of the Speech Recognition/Speaker Detection/Confidence Analysis stages exist for uploaded content today.
2. **No video-specific storage or pipeline at all.** `media-urls.js`/`sw.js` treat video extensions identically to audio (pass-through), but no backend module handles video upload, storage, or processing — "video books" would be entirely new.
3. **Word-timestamp distribution across blocks is approximate, not exact**, for chapter narration (proportional-by-character-length slicing, `server.py:1215-1238`) — a real accuracy gap if "synchronization accuracy is more important than visual effects" is the north star.
4. **No offline support for book content.** `sw.js` explicitly bypasses `/api/*` (all book data) and all audio/video files — offline caching today is app-shell/static-asset only. A student cannot read a previously-opened book offline, let alone play synced audio offline.
5. **Gemini integration is fragmented across 6+ independent HTTP clients** with duplicated prompt-building, retry, and parsing logic. Adding a Smart Books AI pipeline as a 7th independent client would compound this rather than resolve it.
6. **No admin/author configuration surface for reading-experience features.** Every current reader behavior (word highlight, etc.) is hardcoded and always-on; there is no per-book settings object analogous to `book_factory_interaction_planner.py`'s tier policy for the *reading* experience.
7. **`coverImage` has no validation.** A manually-pasted URL is never checked for reachability, format, or ownership — a broken or hostile URL would only surface as a broken `<img>` at read time.

## 8. Risks

- **Duplicating Gemini plumbing a 7th time** instead of consolidating — increases maintenance surface exactly where the codebase already shows strain.
- **Building a new ASR pipeline touches nothing existing today**, so it carries no *regression* risk to current books, but every new provider integration (whichever ASR/STT vendor is chosen) needs its own budget, retry, and fallback discipline matching the existing `BFRetryableError`-style taxonomy — skipping that discipline is how the fragmentation in gap #5 happened.
- **Retrofitting sync data onto existing published books** (if ever desired) means re-processing potentially thousands of already-live chapters — this should stay strictly opt-in per the existing "additive, non-destructive" convention (`CLAUDE.md`), never a forced migration.
- **R2-or-nothing paths (Hero Artwork) show a real failure mode**: if a future Smart Books media pipeline follows that pattern without a GridFS-style fallback, an R2 outage or misconfiguration would hard-fail content, not degrade gracefully like narration audio does today.
- **Cover-image URL field has zero validation** — extending "media" to include arbitrary uploaded video without validation would be a bigger version of the same latent issue.

## 9. Opportunities to Reuse Existing Components

- **`book_factory_narration.py`'s pattern** (pure, idempotent, side-effect-free block-type transform) is the right template for any new "convert raw content into sync-ready blocks" step — it should be extended, not replaced, for video/uploaded-audio.
- **`ChapterBlocks.jsx`/`DialogTurn.jsx`'s existing word-highlight engine** already has the binary-search-over-timestamps core and the two-mode (exact/estimated) fallback discipline a broader teleprompter needs — extend its data contract (add sentence/paragraph spans) rather than building a parallel highlighting system.
- **`book_factory_interaction_planner.py`'s tier/density policy model** is a directly reusable template for "admin configures features per book" — the same deterministic, pure-function, budget-based approach should govern which sync/teleprompter features a book exposes.
- **R2-first/GridFS-fallback pattern** (`server.py`'s `_upload_audio_to_r2` + `audio_bucket` fallback) is the proven, graceful-degradation storage pattern to replicate for any new media type — not Hero Artwork's R2-or-nothing pattern.
- **`book_factory_jobs.py`'s atomic per-stage claim/attempt-fencing state machine** (proven safe under concurrent access, modeled after `camrapidpay_payment_tools.py`'s own atomic-claim discipline verified extensively this session) is the right foundation for a new "media processing pipeline" job type — one more stage type in the same job document, not a new job engine.
- **`premium_ai_tools._post_gemini`** is the closest existing shared Gemini primitive — a consolidation effort should start by moving other call sites onto it rather than inventing a new shared client.

## 10. Phased Implementation Roadmap

**Phase 0 — Universal Synchronization Foundation.** Establish the platform contract only — no AI provider integration, no uploads, no speech recognition, no alignment, no frontend behavior changes, no Reader modifications. Deliverables: the canonical synchronization schema, synchronization versioning, provider interface contracts, the storage model, the Reader consumption interface, and the Review Studio data contract — all defined in full in [`universal-synchronization-engine-technical-spec.md`](universal-synchronization-engine-technical-spec.md). The objective is to stabilize the contract before any provider is wired to it.

**Phase 1 — Consolidate before extending.** Extract one shared Gemini HTTP client (building on `book_factory_gemini.py`'s retry taxonomy + `premium_ai_tools._post_gemini`) and migrate the fragmented call sites onto it. Zero user-facing change; pays down gap #5 before it gets a 7th sibling.

**Phase 2 — Media processing pipeline for uploaded audio (audio books only).** Add an upload route + storage (R2-first/GridFS-fallback, matching the proven pattern) + one new ASR/forced-alignment stage in `book_factory_jobs.py`'s existing state machine, producing canonical schema output (Phase 0) that also backs the existing `{word, start, end}` shape `ChapterBlocks.jsx` already consumes — no Reader-side changes needed for this phase.

**Phase 3 — Extend the highlight engine to sentence/paragraph granularity + admin config.** Add sentence/paragraph spans to the existing timestamp data (additive fields, not a schema replacement), and a per-book settings object modeled on `book_factory_interaction_planner.py`'s tier policy (`enableTeleprompter, enableWordHighlight, enableSentenceHighlight, ...`) — realized as the "reading profiles" defined in the tech spec. Reader reads the config and adapts — no new book "format."

**Phase 4 — Karaoke/shadowing/storytelling modes + auto-scroll + playback speed + replay.** Pure Reader-side UI work against the data model established in Phases 0-3; no new backend capability required.

**Phase 5 — Video books.** Only after 0-4 prove the sync model on audio: add video upload/storage + audio-extraction stage feeding the *same* ASR pipeline from Phase 2, per the tech spec's "treat audio and video identically" principle.

**Phase 6 — Offline support for book content**, evaluated last since it's explicitly called out as "where applicable" — likely scoped to already-opened books only, given the deliberate app-shell-only caching decision already in `sw.js`.

Each phase preserves every existing book, requires no migration of published content, and the manual-authoring path is never touched.

## 11. Recommended Smart Books Engine Architecture (extends, does not replace)

```
                 ┌─────────────────────────────────────────┐
                 │   Existing: book_factory_jobs.py state    │
                 │   machine (atomic claim, attempt-fencing) │
                 └───────────────┬───────────────────────────┘
                                  │  + one new stage type
                                  ▼
         Upload (new) ──▶ Storage (existing R2/GridFS pattern)
                                  │
                                  ▼
                 Audio extraction (video only, new)
                                  │
                                  ▼
              ASR + forced alignment (new provider integration,
              same retry/fallback discipline as book_factory_gemini.py)
                                  │
                                  ▼
      Existing shape: {word, start, end} ──▶ NEW: sentence/paragraph spans
                                  │
                                  ▼
        book_factory_narration.py-style block transform (existing pattern,
        extended) writes transcript/dialog blocks exactly as today
                                  │
                                  ▼
              Same manual-review handoff to StudioEditor (unchanged)
                                  │
                                  ▼
                    db.books, same schema + additive fields
                                  │
                                  ▼
   Reader: ChapterBlocks.jsx / DialogTurn.jsx highlight engine (existing,
   extended with sentence/paragraph modes) + NEW per-book config object
   (modeled on book_factory_interaction_planner.py's tier policy)
```

One synchronization engine, one data shape (`{word,start,end}` plus new sentence/paragraph spans), one job-state-machine, one storage pattern — used identically whether the source was ElevenLabs TTS (today) or uploaded audio/video (new). Content type (text-only, audio, video, conversation, storytelling, mixed) is a matter of *which blocks a chapter contains*, exactly as it is today — never a separate engine.

## What was explicitly searched for and not found

- Claude/Anthropic API integration — not found anywhere in either repository.
- A literal "teleprompter" module — not found by that name; the equivalent capability exists as the word-highlight system described in §6.
- ASR/speech-recognition/forced-alignment for uploaded (non-AI-generated) media — not found.
- Video upload or storage pipeline — not found.
- Book-content or media offline caching — not found; `sw.js` is app-shell/static-asset only by deliberate design.
- A shared/unified Gemini client — not found; integration is fragmented across 6+ modules (see §3, §7).
